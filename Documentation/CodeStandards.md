# SqueHub source documentation standard

Health checks return only bounded, safe summaries and codes. Liveness must not touch external dependencies; readiness probes only selected or explicitly required dependencies. Doctor is read-only by default and never repairs infrastructure. Bound network probes; package checks must set their own timeouts. Use `App\Plugins\Health` in application examples and canonical `App\Health` contracts in framework internals. See [Health](Health.md).

This is the permanent comment standard for first-party SqueHub code under `App`, `Bootstrap`, `Config`, `Database`, and `Project`. Keep source readable and maintain comments whenever behavior changes.

Application-facing examples should import available `App\Plugins` symbols. Framework internals, legacy compatibility explanations, and types without a Plugins entry keep their canonical namespaces. The [Plugins inventory](Plugins.md) identifies supported public imports.

- Give significant framework classes a concise contract: responsibility, owner, lifecycle, and boundaries with neighboring systems. A file-level comment can serve the same purpose for bootstrap and configuration scripts.
- Document public or protected methods when their side effects, failure behavior, compatibility rules, or return semantics are not clear from the signature. Use PHPDoc shapes and exception tags where static analysis or callers benefit.
- Explain security decisions at the check that enforces them: token comparison, input redaction, SQL binding, output escaping, and exclusions. Never include secret values in a comment, log, or example failure message.
- Explain compatibility branches: which legacy API is preserved, why it remains, and which v2 service owns the behavior. Update comments when that ownership changes.
- Comment private algorithms only where an invariant or edge case is easy to miss, such as flash generations, partial Model identity, pivot isolation, migration transaction limits, or route matching order.
- Do not restate obvious assignments, signatures, or loop mechanics. Avoid decorative banners, emoji headings, generated-sounding narration, invented authorship, and comments on every line. Remove stale comments instead of preserving incorrect descriptions.

Professional comments should help a maintainer safely modify the code, not increase comment volume. New framework work and changes to existing classes should follow this policy.

For Application Contract changes, comment the boundary between declared public behavior and runtime enforcement. Route, Resource, schema, and outgoing Webhook declarations must be explicit and side-effect free during export. Explain why contract generation reads only reviewed public metadata, why secrets and live request data never become examples, and why OpenAPI is an export bridge rather than SqueHub's internal model. Keep framework code on canonical `App\Api\Contract` types and application examples on `App\Plugins\Contract` and `ContractSchema`; `App\Plugins\Schema` remains the database schema API.

This standard applies to **all existing and new first-party PHP source** under `App`, `Bootstrap`, `Config`, `Database`, and `Project`. Every significant class, interface, trait, or enum needs a purpose and contract comment. Classless bootstrap and configuration files need a concise file comment when their loading role is not obvious. Document public and protected methods whose side effects, failure behavior, compatibility rules, or return semantics are not clear from native types. Give complex array shapes accurate PHPDoc where it helps callers or static analysis.

Security comments belong beside the enforcing code: redaction, SQL binding and identifier validation, CSRF checks, session rotation, safe redirects, and HTML escaping. Legacy bridges should name the old contract and the v2 service now responsible for it. Remove stale descriptions when behavior changes. Obvious assignments, simple getters, and mechanical loops need no narration. Never add decorative banners, invented authors, or generated-style phrases such as “Now we,” “This method simply,” or “Generated by.”

Logging and request diagnostics follow the same rules. Comments should make clear that automatic metrics keep no SQL or bindings, that HTTP correlation IDs are framework generated, and that structured log context does not traverse arbitrary objects.

Cache comments should explain namespace containment, key and value validation, lock ordering, corruption handling, and the boundary with compiled views. Keep cache keys and payloads out of exception and diagnostic examples.

Event comments should describe lazy class-listener resolution, priority and registration order, snapshot-on-dispatch behavior, explicit stopping, caller-owned transaction semantics, and aggregate-only diagnostics. Queued listeners need explicit class registration and a `QueueableEvent` JSON payload; scheduling follows snapshot priority, while worker execution order is not guaranteed across workers. Document the after-commit boundary and Queue-owned retries without implying that a later listener can undo an already scheduled job. Do not include event payloads in framework exception or logging examples.

For view and browser-form changes, document the escaped versus explicit raw output boundary, why compiled templates cannot retain session values, which requests may become a redirect-back destination, and how flashed errors and old input expire. Put security comments beside the checks that enforce these rules. Keep examples free of secrets and do not describe legacy direct-header redirects as returnable responses.

For Storage changes, document the distinction between logical and physical paths, containment and link checks, reserved internal names, atomic replacement, lock ordering and scope, recursive deletion safety, and stream ownership. Keep raw paths, filenames, and file contents out of automatic diagnostics and exception messages. Recheck failure cleanup as well as successful operations.

For Authentication changes, document the read-only versus stateful guard boundary, the identity provider's persistence role, session ID rotation before identity storage, whole-session logout, stale identity clearing, and request-only user caching. Explain dummy password verification and rehash ordering without exposing credentials. Keep automatic diagnostics aggregate-only, and never put identity or password values in framework exceptions or logs.

For personal access tokens, document why the raw secret is returned only at issuance, why the repository stores a one-way digest and a separate opaque lookup identifier, and how named guards select one request identity without changing session authentication. Keep token abilities distinct from Authorization permissions. Explain expiry, revocation, atomic rotation, throttled last-used writes, and the database migration boundary beside the enforcing code. Parse only a strict Bearer header, never URL/body/cookie token values. Redact the raw token, digest, Authorization header, identity and ability names from automatic diagnostics and safe exceptions. CSRF exclusions for dedicated token-only paths must be explicit; never make all API paths exempt because a token guard exists. Application-facing middleware and result types need exact `App\Plugins` symbols while internal repositories remain canonical-only.

For Authorization changes, document guest default deny, exact policy mappings, lazy Container resolution, and the boundary between legitimate 403 denials and configuration or policy failures. Explain why explicit identity contexts do not mutate Auth, why decisions are evaluated each time, and why middleware accepts only global abilities. Keep automatic diagnostics aggregate-only; never store identities, subjects, ability names, or denial messages there.

For account-security changes, explain why Sessions store a credential fingerprint, why a mismatch clears stale authentication, why plaintext tokens are returned once while only their hashes are stored, and why reset/verification tokens bind to credential or address context. Keep one-time claim ahead of account mutation and document that a failed later write still consumes the token. Rate limiting and delivery are separate features. Do not automatically log credentials, token values, or account existence; keep diagnostics aggregate-only.

For rate-limit changes, document why raw keys are fingerprinted, why counters require atomic storage rather than Cache reads and writes, why denials do not extend a fixed window, and why corrupt file state fails closed. Describe local lock scope without claiming distributed guarantees. Keep limiter names, keys, fingerprints, and policy configuration out of automatic diagnostics; do not infer an IP identity from untrusted proxy headers. Auth and Account Security remain policy-neutral.

For lock, idempotency, retry, and circuit-breaker changes, name the exact resource and coordination backend, lease or retention boundary, ownership check, crash behavior, and failure mode at the enforcing code. A token-checked release is not external fencing; an idempotency result is not a transaction over third-party side effects; a retry may repeat an unsafe mutation; and a circuit only gates attempts in its selected state store. Document local-file versus shared-service guarantees without treating network filesystems as tested distributed locks. Hash potentially sensitive keys before persistence, keep ownership tokens and request or response bodies out of diagnostics, and make backend corruption fail visibly. Application examples use the matching `App\Plugins` types; internals use canonical subsystem classes. See [Locks](Locks.md), [HTTP idempotency](Idempotency.md), [Retries](Retries.md), and [Circuit breaker](CircuitBreaker.md).

For Mail changes, document sender and recipient validation before SMTP I/O, why each SMTP send gets a fresh client, the boundary between authored HTML and framework header safety, and the compatibility status of `App\Core\Mail`. Keep message content, addresses, credentials, and provider error details out of automatic diagnostics and framework exceptions. Account token delivery is composed by application code; Mail does not issue tokens or choose security policy.

For Notifications changes, document Application ownership, explicit recipient routes, lazy channel resolution, ordered delivery, and the stop-on-first-failure rule. Queueable Notifications must use the existing QueueJob path, an explicit JSON-safe Notification payload, and an explicit recipient identity or anonymous route. Keep notification objects, account tokens, recipient data, and channel payloads out of automatic diagnostics and framework exception text. The Array channel records only class names. Distinguish delivery notifications from the historical session-flash Notification helpers.

For Queue changes, document the at-least-once contract, why payloads use explicit versioned JSON reconstruction, and why reservation claims and settlement are fenced by a random token. Explain retry, dead-worker recovery, failed-record atomicity, nested savepoint callback behavior, and the limits of worker shutdown. Failed-job retry retains sensitive payloads; protect Database or Redis access and backups. Keep payloads and arbitrary exception messages out of safe failed-job metadata, diagnostics, CLI output, and automatic logs. Immediate dispatch and explicit `afterCommit()` have different transaction timing; do not claim that post-commit Queue persistence can roll back a committed business transaction. Document the Windows soft timeout limitation and external supervisor responsibility. Redis Queue changes must preserve atomic claim/settlement, bounded scripts, server-time semantics, Queue-owned key isolation, and shared restart signaling; never add a fallback from persistent Queue to `sync`.

Queue compositions must use the existing QueueJob codec and worker. Keep chain advancement, batch terminal counts, and cancellation fenced by the current reservation; a retry or stale acknowledgement must not advance progress twice. Store dormant chain payloads only until they become runnable or terminal, and treat active metadata as part of worker correctness when reversing its migration. Expose only bounded status counts through operational tools. A supervisor, not `queue:status`, establishes worker liveness.

Broadcasting is optional and application-selected. Require explicit bounded JSON data and channel names; never infer a broadcast from every internal Event or serialize a Model, Request, Session, or arbitrary object graph. A private channel needs an Application-owned rule evaluated against the current authenticated server identity at subscription time; publication alone grants no browser access. Keep adapter construction lazy, fail closed on rule or adapter errors, and use the ordinary QueueJob path for deferred publication with at-least-once semantics. Do not claim that Redis Pub/Sub or the core adapter contract supplies a WebSocket server. Provider-specific CSP `connect-src` remains an application deployment choice.

Queued framework features must implement QueueJob and never persist arbitrary native PHP serialization. Treat every Queue payload, including retained failed payloads, as sensitive persisted data, even when diagnostics and CLI listing redact it. Normal application-facing contracts receive `App\Plugins` symbols; framework internals depend on canonical subsystem types, never the Plugins gateway. Mail and Notification delivery use Queue's retries and workers instead of creating parallel retry infrastructure.

For Scheduler changes, document the difference between a unique occurrence claim and an expiring overlap lock. Explain UTC occurrence identity, local-time and DST evaluation, why queued jobs cannot use execution-lifetime overlap protection, and why a crash does not automatically replay a claimed minute. Persist only safe hashed task identities and status; keep task arguments, Queue payloads, and application exception text out of diagnostics and CLI output. Keep schedule definitions in `Project/Scheduler/` or a package `Scheduler/` directory; never load definitions or run tasks during normal Application boot.

For Kit changes, keep static manifest discovery separate from deliberate lifecycle execution. Comment exact-case identity checks, relative-path containment, ownership fingerprints, stale-plan rejection, and partial-effect reporting where they are enforced. A Kit hook is trusted, unsandboxed PHP and runs only during its explicit lifecycle operation; preview, Doctor, contract export, Dev, and normal HTTP boot must not include Kit entry PHP. Distinguish Kit-owned published files from effective application/Package runtime registrations. Never imply that disabling a Kit deletes generated files, that Kit removal rolls back Migrations or Seeders, or that its reviewed plan can reverse arbitrary hook side effects. Kit author examples use `App\Plugins\Kit` and `KitContext`; framework internals use `App\Kits`.

For Redis changes, keep Redis optional and its socket, authentication, database selection, and capability probes out of normal Application boot. Hold credentials as sensitive configuration and never include client errors, URLs, keys, values, prefixes, or endpoints in safe exceptions and automatic diagnostics. Use canonical `App\Redis` contracts internally; `App\Plugins` remains backend independent. Cache values use a validated, versioned scalar/array codec; native Session payloads remain PHP-managed. Explicit Redis drivers never fall back. `auto` probes only at subsystem resolution, makes one deterministic choice per Application lifetime, and never switches backends per operation. Redis credentials belong in Redis configuration. Every subsystem key needs its own namespace; Cache clear must use scoped incremental scanning and never flush a shared database.

For outgoing HTTP, use canonical `App\HttpClient` contracts internally and `App\Plugins\Http` in application examples. Keep TLS certificate and hostname verification on by default, reject unsafe schemes and injected headers, and avoid URL, credential, body, or response content in automatic diagnostics and safe exceptions. A retry is an explicit application decision because non-idempotent requests may repeat side effects. Prefer Application-scoped HTTP fakes or loopback fixtures to external internet calls in tests. Incoming `App\Http` types remain separate.

## Application-facing Plugins import

Application code may import `App\Plugins\Route`, `App\Plugins\View`, `App\Plugins\Model`, `App\Plugins\DB`, `App\Plugins\Cache`, `App\Plugins\Storage`. These entries delegate to the current subsystem; canonical imports and global helpers remain supported. See [Plugins](Plugins.md) for the complete mapping and compatibility rules.

Future SqueHub features intended for normal application use must provide an appropriate `App\Plugins` entry alongside their canonical API. Framework internals must depend on canonical subsystem contracts, never on the Plugins convenience layer.
## Cryptography and secrets

Use established authenticated primitives through `App\Plugins\Crypt` for recoverable application secrets; framework internals use canonical `App\Cryptography` contracts. Never build a custom cipher, disable authentication, or encrypt passwords instead of hashing them. Version encrypted formats, bind values to a stable purpose when contexts must be separate, and keep keys and input values out of diagnostics. Do not use native PHP serialization for encrypted values. New application-facing cryptographic APIs need Plugins exposure. See [Cryptography](Cryptography.md).
